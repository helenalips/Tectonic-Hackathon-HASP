# TrustGrid data contract

Owner: orchestrator. Agents 1-4 build against this file and `openapi.yaml`.
Nobody changes either file without the orchestrator.

The SQLModel implementation of this contract lives in `backend/app/models.py`.
List-valued fields (`domains`, `countries`, `linked_document_ids`, ...) are stored as JSON columns.
All ids are short strings with a type prefix (`cl-`, `p-`, `doc-`, `di-`, `clm-`, `ev-`, `cf-`, `sol-`, `u-`).
All timestamps are ISO 8601 UTC. All dates are `YYYY-MM-DD`.

## 3. Claim key taxonomy and normalization

Fixed list. The LLM and the mock rules may only emit these keys. Unknown keys are dropped.

| Key | Value format | Unit | Example |
|---|---|---|---|
| `discount_pct` | decimal string, no `%` | `%` | `10` |
| `price_model` | enum `full_price \| discounted \| fixed_fee` | – | `full_price` |
| `headcount` | integer string | `employees` | `350` |
| `headcount_target` | integer string | `employees` | `2000` |
| `go_live_date` | `YYYY-MM-DD` | – | `2026-01-01` |
| `payroll_frequency` | enum `monthly \| semi_monthly \| biweekly \| weekly` | – | `monthly` |
| `payroll_country` | ISO code | – | `ET` |
| `payroll_provider_count` | integer string | `providers` | `1` |
| `hr_system` | lowercase product name | – | `sap successfactors` |
| `self_service_status` | enum `live \| planned \| not_planned` | – | `planned` |
| `sla_response_hours` | integer string | `hours` | `24` |
| `pay_gap_method` | lowercase short label | – | `integrated system with job architecture` |
| `contact_person` | Person id | – | `p-jan` |
| `declined_scope` | module label: `digital time registration \| shift planning \| employee self-service app` | – | `digital time registration` |
| `payroll_cutoff_day` | integer string 1-31 (day of month) | `day of month` | `20` |
| `invoice_terms_days` | integer string 1-180 | `days` | `30` |

Normalization (applied before any comparison): trim, lowercase, `10 %`/`10%`/`ten percent` → `10`,
`1.000`/`1,000` → `1000`, dates in any common form → ISO, `€`/`EUR` stripped into `unit`.

"Semantically similar key" for conflict detection means: same key, or keys in the same group:
`{discount_pct, price_model}`, `{headcount, headcount_target}`.
A `price_model = full_price` claim conflicts with an active `discount_pct > 0` claim.

v2 additions:
- `declined_scope` is multi-valued: a client can decline several modules, so two `declined_scope` claims never
  conflict with each other. It is extracted when a sentence names a module next to a decline marker
  ("decided to keep paper time registration", "declined the shift planning module", "do not propose a digital
  clocking system"). A text that PROPOSES a declined module ("we propose a digital clocking system") conflicts
  with the active `declined_scope` claim for that module (severity high). Proposals are detected by the live
  draft check only; they are never stored as claims.
- `payroll_cutoff_day`: "cut-off is on the 20th", "the 25th is the payroll cut-off" → `20`, `25`. Dates
  ("cut-off on 15 March 2026") are not cut-off days.
- `invoice_terms_days`: "payable within 30 days", "payment terms of 45 days", "60 days net" → `30`, `45`, `60`.
- Severity: high for `discount_pct`, `price_model`, `invoice_terms_days`, `declined_scope`; medium for
  headcounts, dates, counts, `sla_response_hours`, `payroll_cutoff_day`, `contact_person`; low otherwise.

## 5. Dedup thresholds (single source; Agent 2 reads them from `config.py`)

| Level | Rule |
|---|---|
| Document | same `content_hash`, or cosine ≥ **0.95**, same `client_id` only |
| Claim | same `client_id + key + normalized value` among `active` claims |
| DossierItem | same `client_id + category`, `status = open`, cosine ≥ **0.85** |

Cross-client matching is never allowed for dedup. Only the vertical check reads other clients,
and it returns only the solution pattern, the date and the expert (never client figures).

## 6. Trust score

| Factor | Weight | 1.0 when | 0.0 when |
|---|---|---|---|
| recency | 0.20 | updated ≤ 90 days ago | > 3 years (linear in between) |
| ownership | 0.15 | owner set | no owner |
| country_relevance | 0.15 | `country_scope` = client country or `MULTI` | other country |
| author_expertise | 0.20 | 0.5 × domain match + 0.5 × person reliability | |
| corroboration | 0.15 | ≥ 3 evidence rows | 1 evidence row (0.5 at 2) |
| no_open_conflicts | 0.15 | no pending conflict touches it | any pending conflict |

Labels: ≥ 75 **Reliable**, 50-74 **Verify**, < 50 **Uncertain**. `suspicious` documents are capped at 40.

Person reliability = 100 × (0.6 × confirmed-share + 0.2 × (1 − conflict-share) + 0.2 × currency),
where confirmed-share = share of their origin claims with ≥ 1 confirmation, conflict-share = share involved
in a conflict resolved against them, currency = share of their documents updated in the last 12 months.
Persons with < 2 claims get 60 with the reason "Limited track record".

## 8. Security-relevant contract rules

- Every request and response body is a strict Pydantic model (`extra = "forbid"`).
- `password_hash`, `content_hash` internals and AuditLog are never exposed to consultants.
- `POST /check` is read-only: it never stores documents, claims, conflicts or dedup decisions; it writes one
  AuditLog `view` row (entity `check`, no text). A suspicious draft returns no findings.
- Cross-client results (`/search/precedents`, vertical check, `/check` similar cases, problem expert) return only:
  `client_label` (sector + country, not the client name, unless the user is assigned or lead/admin),
  `category`, `resolution_summary` (figures masked), `date`, `expert`, `similarity`.
